# 扩展机制设计方案

文档状态：阶段 1（解码器接口）、阶段 2（结果发布）、阶段 3（外部进程插件与管理页）已实施并验收；阶段 4、5 未开始。  
日期：2026-10-26。  
前置文档：[performance-design.md](performance-design.md)（下称“性能方案”）。

## 1. 目标与范围

让同一条低延迟链路（采集 → GPU 预处理 → 推理 → GPU 后处理 → 呈现）服务不同领域，而不为每个领域分叉代码。

原则：

- **越靠近实时路径，接口越窄、约束越严。** 实时路径上的扩展必须遵守性能方案的资源与时序约束（第 4.3 节），并纳入同一套计时；离开实时路径的扩展不得反向阻塞它。
- **能声明就不写代码。** 模型差异优先用清单描述，只有清单表达不了的输出格式才需要解码器代码。
- **先内部、后公开。** 接口先在本仓库内用至少三种实现验证，稳定后再定为对外 ABI。
- **不做通用管线图。** 不提供 GStreamer 式的任意元件拼接：拼接自由度会使延迟无法保证，也无法按性能方案第 7 节的口径测量。

非目标：采集源扩展（摄像头、视频文件、网络流）。现有 `CaptureSource` 接口在技术上可以开放，但这会把定位从屏幕与窗口检测改为通用视觉管线，需另行决定。

## 2. 领域差异与扩展点

| 差异 | 例子 | 是否在实时路径 | 扩展层 |
| --- | --- | --- | --- |
| 模型与输出格式 | 检测、姿态、分割、旋转框；一对多头与端到端头 | 是 | 第 1 层：模型适配 |
| 结果的使用方式 | 告警规则、记录、推送到其他系统、驱动自动化 | 否 | 第 2 层：结果发布 |
| 参数与界面 | 各领域自己的设置项与面板 | 否 | 第 3 层：设置与界面 |

## 3. 总体结构

```
 采集 ─▶ 复制 ─▶ 预处理 ─▶ 推理 ─▶ [解码器] ─▶ 回读 ─▶ 覆盖层
                                    第 1 层        │
                                                   └─▶ [结果发布] ─▶ 其他进程（任意语言）
                                                          第 2 层
 界面 ◀─ [设置项声明] 第 3 层
```

宿主始终拥有线程、CUDA stream、显存分配与计时；扩展只在宿主给定的位置和资源内工作。

## 4. 第 1 层：模型适配

### 4.1 模型清单

模型文件旁的同名 JSON（`model.onnx` → `model.json`）。低精度版本沿用 FP32 版本的清单（`*-fp16.onnx` 查找 `*-fp32.json`）。导出脚本生成，也可手写。

| 字段 | 含义 | 缺省 |
| --- | --- | --- |
| `decoder` | 解码器名称，见 4.4 | 按输出形状推断（取 `outputs` 记录的形状，或引擎的实际形状），只能推断检测头 |
| `imgsz` | 输入边长 | 取引擎输入形状 |
| `class_names` | 类别号 → 名称 | 以类别号显示 |
| `keypoints.count` | 每个目标的关键点数 | 0 |
| `keypoints.names` | 关键点名称 | 无 |
| `keypoints.skeleton` | 连线，关键点下标对的数组 | 无 |
| `preprocess.resize` | `letterbox`（等比例缩放加填充，填充值 114） | `letterbox` |
| `preprocess.color` | `rgb` 或 `bgr` | `rgb` |
| `preprocess.scale` | 像素值乘数 | `1/255` |

当前预处理内核只实现了缺省组合。清单声明了其他组合时，启动阶段明确拒绝，不静默按缺省值运行。

### 4.2 统一结果格式

每帧结果为固定容量的结构，写在显存中，由宿主一次回读到页锁定内存：

- 目标：`x1, y1, x2, y2, score, cls`，坐标为屏幕物理像素（已去掉填充、除以缩放比例并加上检测区域原点）。
- 关键点：每个目标 `keypoints.count` 个 `x, y, score`，坐标系与目标框相同。不含关键点的模型不回读这一段。
- 统计：最终目标数、超过阈值的候选数、因容量丢弃的候选数。

容量固定（目标 300 个，每个目标最多 32 个关键点），与性能方案 5.1 的固定容量后处理一致。分割掩码因体积和回读成本另行设计，不在本版本内。

### 4.3 解码器契约

解码器把推理输出张量解码为 4.2 的结果。实时路径上的约束：

1. 只在宿主给定的 CUDA stream 上排队工作，不调用任何同步接口，不切换设备。
2. 显存在启动时一次分配；每帧不申请、不释放显存。
3. 结果写入宿主提供的显存结构，不得超过容量；溢出时如实填写统计字段。
4. 每帧执行时间计入“后处理”阶段，与其他阶段一样按分位数报告。
5. 读取阈值等运行时参数只能通过每帧传入的参数，不得自行读取外部状态。

接口（阶段 1 为仓库内部的 C++ 接口）：

```cpp
class OutputDecoder {
 public:
  virtual ~OutputDecoder() = default;
  virtual const char* Name() const = 0;
  virtual int NumClasses() const = 0;
  virtual int NumKeypoints() const = 0;
  // 实时路径：在 stream 上排队解码，结果写入 output（显存）
  virtual void Enqueue(const float* modelOutput, const DecodeParams& params, DetectionOutput* output,
                       cudaStream_t stream) = 0;
};
```

### 4.4 内置解码器

| 名称 | 输出形状 | 处理 | 正确性基准 |
| --- | --- | --- | --- |
| `yolo-anchors` | `[1, 4 + nc, N]` | 单标签筛选、按类别 NMS（现有实现） | 重构前后 COCO mAP 相同；同一输入与 Python 参考一致；候选不溢出时结果可重复 |
| `yolo-end2end` | `[1, K, 6]`，每行 `x1, y1, x2, y2, score, cls` | 阈值筛选，无 NMS | Python 参考解码在同一引擎输出上一致；COCO mAP 记录 |
| `yolo-pose-anchors` | `[1, 4 + 1 + 3k, N]` | 同 `yolo-anchors`，附带关键点 | Python 参考解码一致；参考解码与 Ultralytics 对同一 ONNX 的预测一致 |

三种实现覆盖“需要 NMS / 不需要 NMS / 附带每目标数据”三种情况，用来检验 4.3 的接口是否站得住。

`yolo-anchors` 原定的“重构前后逐框一致”无法作为基准：重构前的实现在分数并列时按候选写入位置（原子操作的先后）排序，同一程序两次运行就有 2362 张图结果顺序不同。重构中改为以锚点号为第二键（性能方案 5.1），因此改用上表三项。

验收结果（2026-10-26，RTX 4050 Laptop）：

| 解码器 | 模型 | 同一输入与 Python 参考 | 其他 |
| --- | --- | --- | --- |
| `yolo-anchors` | YOLO26n FP16 | 200 张一致率 1.000 | COCO 5000 张 mAP50-95 40.31、mAP50 56.01，与重构前相同；候选不溢出的 4537 张两次运行完全一致 |
| `yolo-end2end` | YOLO26n 端到端 FP32 | 200 张一致率 1.000 | COCO 5000 张 mAP50-95 40.24、mAP50 55.78；输出已按分数降序，参考解码与 Ultralytics 预测逐框相同 |
| `yolo-pose-anchors` | YOLO26n-pose FP32 | 200 张一致率 1.000；关键点坐标最大差 0.00006 px，分数最大差 1e-6 | 参考解码与 Ultralytics 对同一 ONNX 的预测一致（关键点裁到图像内后） |

空载端到端（144 FPS 测试源）：一对多头 FP16 取得→结果 P50 1.48 ms、P95 2.50 ms，与重构前一致；端到端头 FP32 为 2.51 / 3.74 ms，姿态 FP32 为 3.17 / 4.24 ms（两者只有 FP32 版本，推理本身分别约 2.0 与 2.5 ms）。

### 4.5 解码器插件的对外 ABI（阶段 4）

接口稳定后以纯 C ABI 公开，原生插件为 DLL：

- 导出单个查询函数，返回函数表；函数表与所有参数结构的第一个字段为结构大小，后续版本只追加字段。
- 跨边界只传 C 结构、指针与 UTF-8 字符串，不传 C++ 对象、STL 容器或异常。
- 插件声明所需的接口版本，宿主拒绝不兼容的插件并在界面说明原因。
- 原生插件与宿主同进程，享有完全权限；宿主只加载用户显式放入插件目录的 DLL。

## 5. 第 2 层：结果发布

### 5.1 机制

宿主在每帧结果可用后，把结果写入一块命名共享内存，并通知等待者。任何语言的程序都可以读取，读取方崩溃或卡顿不影响检测。

- 共享内存：`Local\NeuralReflex.Results.v1`。
- 通知：两个手动重置事件 `Local\NeuralReflex.Results.v1.Event0`、`...Event1`。第 k 帧发布时，宿主先重置 `Event[(k+1) % 2]`，写入数据，再设置 `Event[k % 2]`。读取方读完第 s 帧后等待 `Event[(s+1) % 2]`。这样任意数量的读取方都不需要注册，也不会空转。
- 一致性：序号锁（seqlock）。写入前序号加一（变为奇数），写完再加一（变为偶数）；读取方复制前后读到的序号相同且为偶数，才算读到完整的一帧。

### 5.2 布局（版本 1）

所有字段小端序，偏移固定：

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0 | `uint32` | 魔数 `0x5352524E`（字节序列 `NRRS`） |
| 4 | `uint32` | 布局版本，1 |
| 8 | `uint32` | 映射总字节数 |
| 12 | `uint32` | 帧记录偏移 |
| 16 | `int64` | 帧序号锁（偶数时帧记录完整，已发布帧数 = 序号 / 2） |
| 24 | `int64` | 元数据序号锁 |
| 32 | `uint32` | 元数据偏移 |
| 36 | `uint32` | 元数据容量 |
| 40 | `uint32` | 元数据实际长度 |
| 44 | `uint32` | 宿主进程号 |
| 48 | `int64` | QPC 频率 |

元数据为 UTF-8 JSON，会话开始时写入（`state` 为 `running`），结束时改写为 `stopped`：

| 字段 | 含义 |
| --- | --- |
| `layout` | 布局版本 |
| `session` | 会话号（开始时刻的 Unix 毫秒数） |
| `state` | `running` 或 `stopped` |
| `pid` | 宿主进程号 |
| `model` | 模型文件名（不含扩展名） |
| `decoder` | 解码器名称 |
| `inputSize`、`numClasses` | 模型输入边长、类别数 |
| `classNames` | 类别号 → 名称 |
| `keypoints` | `count`、`names`、`skeleton` |

帧记录：

| 类型 | 字段 |
| --- | --- |
| `uint64` | 会话内帧号 |
| `int64` | 取得画面时刻（QPC） |
| `int64` | 结果可用时刻（QPC） |
| `int32 × 4` | 检测区域 x, y, w, h（屏幕物理像素） |
| `int32` | 目标数 |
| `int32` | 每个目标的关键点数 |
| `int32` | 超过阈值的候选数 |
| `int32` | 因容量丢弃的候选数 |
| 目标 × 300 | `float32 x1, y1, x2, y2, score; int32 cls`（24 字节），只有前“目标数”个有效 |
| 关键点 × 300 × 32 | `float32 x, y, score`（12 字节），第 i 个目标的第 j 点位于 i × 关键点数 + j |

时间戳用 QPC，读取方可与自己的 `QueryPerformanceCounter` 直接比较，计算结果到达自身的延迟。

### 5.3 代价与约束

- 发布在完成线程上进行，只做一次内存复制和一次事件操作，不分配内存、不加锁、不等待读取方。
- 关闭发布时不创建共享内存。
- 读取示例见 `tools/results/read_results.py`，只依赖 Python 标准库。
- 映射已存在时：发布进程仍在运行则本会话不发布并说明原因，检测照常；发布进程已退出（读取方仍持有映射）则接管，保留序号，读取方以元数据中的会话号区分新旧会话。

验收结果（2026-10-26）：

- 离线模式发布 200 张 COCO 图片，读取方收到的 170 帧（其余发生在读取方打开映射之前）与检测输出逐帧一致，含关键点。
- 实时 144 FPS：读取方收到每一帧，漏帧 0；送达延迟（结果可用 → 读取方取得）P50 约 0.05 ms、P99 约 0.13 ms。
- 读取方运行中被强制结束、随后新读取方接入：检测速率与延迟无变化，新读取方漏帧 0。开启发布时取得→结果 P95 2.57–2.62 ms，未开启时 2.50 ms。
- 另一个进程正在发布时，第二个进程报告占用并照常检测；占用者退出后可再次发布。

### 5.4 后续

本地 WebSocket（便于网页与远程工具接入）在共享内存稳定后加入，作为它的一个读取方实现，不进入完成线程。

### 5.5 外部进程插件（阶段 3）

结果读取方由宿主托管时即为外部进程插件：宿主发现、启动、停止它，崩溃后重启，在界面中显示状态、指标与日志，并把用户设置传给它。插件进程与检测完全隔离，崩溃或卡顿不影响检测，可以用任何语言编写。

**插件包**：一个文件夹，内含 `plugin.json` 与入口程序。宿主在以下目录查找（后者覆盖同 `id` 的前者）：程序目录下的 `plugins`、源码树根目录的 `plugins`（开发时）、`%LOCALAPPDATA%\NeuralReflex\plugins`（用户安装）。

| 字段 | 含义 |
| --- | --- |
| `schema` | 清单格式版本，1 |
| `id` | 唯一标识，小写字母、数字、`-`、`.` |
| `name`、`version`、`description` | 显示用 |
| `api` | 插件协议版本（本节的环境变量、输出协议与 5.2 的结果布局），当前为 1；不等于宿主支持的版本时标为不兼容，不启动 |
| `entry.command` | 可执行文件。含路径分隔符或在插件目录中存在时相对插件目录，否则在 PATH 中查找（如 `python`） |
| `entry.args` | 参数数组，工作目录为插件目录 |
| `settings` | 设置项声明，见第 6 节 |

**生命周期**：启用的插件在宿主启动时启动，与检测会话是否运行无关（插件自行等待结果出现）。有启用的插件时，检测会话自动发布结果。进程异常退出后按 1、2、4…30 s 退避重启；60 s 内退出 5 次则标为失败，不再重启，直到用户重新启用。停止时先关闭插件的标准输入，2 s 后仍未退出则结束进程。插件进程加入宿主的作业对象，宿主退出时一并结束。

**宿主 → 插件**：环境变量。

| 变量 | 内容 |
| --- | --- |
| `NR_PLUGIN_ID` | 插件 `id` |
| `NR_PLUGIN_DIR` | 插件目录 |
| `NR_PLUGIN_DATA` | 插件可写的数据目录（`%LOCALAPPDATA%\NeuralReflex\plugin-data\<id>`） |
| `NR_PLUGIN_SETTINGS` | 设置值，UTF-8 JSON 对象；设置修改后插件重启 |
| `NR_RESULTS_MAPPING` | 结果共享内存名（5.1） |
| `PYTHONPATH` | 前置 Python SDK 目录；同时设置 `PYTHONUNBUFFERED=1`、`PYTHONIOENCODING=utf-8` |

**插件 → 宿主**：标准输出，每行一个 UTF-8 JSON 对象；不是 JSON 的行按日志处理，标准错误按错误日志处理。

| `type` | 字段 | 宿主处理 |
| --- | --- | --- |
| `status` | `text` | 显示为插件当前状态 |
| `metric` | `key`、`value`、可选 `label`、`unit` | 显示在插件详情中，同 `key` 覆盖 |
| `log` | `text`、可选 `level`（`info`、`warning`、`error`） | 保留最近 200 行 |
| `notify` | `text` | 在界面弹出提示，每个插件至多每 2 s 一次 |

**SDK**：`sdk/python/neural_reflex.py`，只依赖标准库，封装设置读取、上述输出协议与结果读取（5.1 的序号锁与事件等待、会话切换）。`tools/results/read_results.py` 使用同一实现。示例插件 `plugins/target-alert`：指定类别的目标连续出现一段时间后提示，并可记录到 CSV，设置项覆盖全部四种类型。

验收结果（2026-10-26，在真实桌面程序中通过 WebView2 远程调试操作界面）：

- 发现与启用：程序发现源码树中的示例插件；在界面中启用后插件以宿主为父进程启动，未开始检测时显示“等待检测开始”。
- 端到端：在桌面程序中开始检测后，因有启用的插件而自动发布结果；插件处理 142.7 帧/秒，送达延迟中位数 0.074 ms；告警按 10 s 间隔触发，界面弹出提示，`alerts.csv` 写入记录。插件运行时检测 144.9 次/秒，取得→结果 P95 1.97 ms。
- 设置：在界面修改“告警类别”后插件收到停止请求、以代码 0 退出并按新设置重启；设置写入宿主设置文件。
- 崩溃策略：连续强制结束 5 次，前 4 次分别在 1、2、4、8 s 后重启，第 5 次标为失败并说明原因；点“重启”后恢复运行。
- 不兼容与无效：协议版本 2 的插件标为不兼容、开关不可用；`settings` 含未知类型的插件标为清单无效并给出原因；两者均不启动。
- 停止：关闭开关后插件以代码 0 退出；关闭桌面程序后插件进程随之结束。

测试中注意到：主窗口最小化时宿主令 WebView2 不可见（`put_IsVisible(false)`），页面暂停处理消息，恢复后由下一条完整快照追上，不需要补发。

## 6. 第 3 层：设置与界面

插件不能修改宿主界面的结构与脚本：宿主界面掌握模型、采集目标与调度设置，插件脚本进入宿主页面即获得全部控制权，也会在宿主界面更新时失效。插件只能通过以下贡献点出现在界面中：

| 贡献点 | 方式 | 阶段 |
| --- | --- | --- |
| 插件管理页 | 宿主列出全部插件：名称、版本、接口兼容性、启用开关、运行状态、指标、日志 | 3 |
| 设置项 | 清单声明，宿主生成表单；值随宿主设置保存，修改后插件重启 | 3 |
| 插件页面 | 插件提供的 HTML，在隔离的 iframe 中加载，只能通过受限的消息接口与宿主通信 | 5 |
| 概览卡片 | 插件推送的指标以宿主样式显示在概览页 | 5 |
| 覆盖层图元 | 插件提交框、点、线、文字，由宿主绘制 | 5 |

设置项（`settings` 数组中每项）：

| 字段 | 含义 |
| --- | --- |
| `key` | 设置名 |
| `type` | `boolean`、`number`、`string`、`enum` |
| `label`、`description` | 显示用 |
| `default` | 缺省值 |
| `min`、`max`、`step` | `number` 的范围 |
| `options` | `enum` 的选项，`[{"value": ..., "label": ...}]` |

宿主按声明校验类型与范围，不合法的值改用缺省值。

## 7. 许可证

本项目以 AGPL-3.0 发布。同进程加载的原生插件（4.5 的解码器插件）通常会被认定为与宿主构成整体作品，需要使用兼容的许可证。外部进程插件（5.5）通过共享内存、环境变量与标准输出交换数据，边界较清楚。公开 ABI 前需确认这一点并写入插件开发说明；本节不构成法律意见。

## 8. 实施阶段与验收

| 阶段 | 交付物 | 完成标准 |
