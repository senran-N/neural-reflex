# 扩展机制设计方案

文档状态：阶段 1（解码器接口）、阶段 2（结果发布）、阶段 3（外部进程插件与管理页）、阶段 6（插件平台，7.2–7.8）已实施并验收；阶段 4、5、7 未开始。  
日期：2026-10-26。  
前置文档：[performance-design.md](performance-design.md)（下称“性能方案”）。

## 1. 目标与范围

让同一条低延迟链路（采集 → GPU 预处理 → 推理 → GPU 后处理 → 呈现）服务不同领域，而不为每个领域分叉代码。

原则：

- **越靠近实时路径，接口越窄、约束越严。** 实时路径上的扩展必须遵守性能方案的资源与时序约束（第 4.3 节），并纳入同一套计时；离开实时路径的扩展不得反向阻塞它。
- **能声明就不写代码。** 模型差异优先用清单描述，只有清单表达不了的输出格式才需要解码器代码。
- **先内部、后公开。** 接口先在本仓库内用至少三种实现验证，稳定后再定为对外 ABI。
- **不做通用管线图。** 不提供 GStreamer 式的任意元件拼接：拼接自由度会使延迟无法保证，也无法按性能方案第 7 节的口径测量。

非目标：采集源扩展（摄像头、视频文件、网络流）。现有 `CaptureSource` 接口在技术上可以开放，但这会把定位从屏幕与窗口检测改为通用视觉管线，需另行决定。

## 2. 领域差异与扩展点

| 差异 | 例子 | 是否在实时路径 | 扩展层 |
| --- | --- | --- | --- |
| 模型与输出格式 | 检测、姿态、分割、旋转框；一对多头与端到端头 | 是 | 第 1 层：模型适配 |
| 结果的使用方式 | 告警规则、记录、推送到其他系统、驱动自动化 | 否 | 第 2 层：结果发布 |
| 参数与界面 | 各领域自己的设置项与面板 | 否 | 第 3 层：设置与界面 |

## 3. 总体结构

```
 采集 ─▶ 复制 ─▶ 预处理 ─▶ 推理 ─▶ [解码器] ─▶ 回读 ─▶ 覆盖层
                                    第 1 层        │
                                                   └─▶ [结果发布] ─▶ 其他进程（任意语言）
                                                          第 2 层
 界面 ◀─ [设置项声明] 第 3 层
```

宿主始终拥有线程、CUDA stream、显存分配与计时；扩展只在宿主给定的位置和资源内工作。

## 4. 第 1 层：模型适配

### 4.1 模型清单

模型文件旁的同名 JSON（`model.onnx` → `model.json`）。低精度版本沿用 FP32 版本的清单（`*-fp16.onnx` 查找 `*-fp32.json`）。导出脚本生成，也可手写。

| 字段 | 含义 | 缺省 |
| --- | --- | --- |
| `decoder` | 解码器名称，见 4.4 | 按输出形状推断（取 `outputs` 记录的形状，或引擎的实际形状），只能推断检测头 |
| `imgsz` | 输入边长 | 取引擎输入形状 |
| `class_names` | 类别号 → 名称 | 以类别号显示 |
| `keypoints.count` | 每个目标的关键点数 | 0 |
| `keypoints.names` | 关键点名称 | 无 |
| `keypoints.skeleton` | 连线，关键点下标对的数组 | 无 |
| `preprocess.resize` | `letterbox`（等比例缩放加填充，填充值 114） | `letterbox` |
| `preprocess.color` | `rgb` 或 `bgr` | `rgb` |
| `preprocess.scale` | 像素值乘数 | `1/255` |

当前预处理内核只实现了缺省组合。清单声明了其他组合时，启动阶段明确拒绝，不静默按缺省值运行。

### 4.2 统一结果格式

每帧结果为固定容量的结构，写在显存中，由宿主一次回读到页锁定内存：

- 目标：`x1, y1, x2, y2, score, cls`，坐标为屏幕物理像素（已去掉填充、除以缩放比例并加上检测区域原点）。
- 关键点：每个目标 `keypoints.count` 个 `x, y, score`，坐标系与目标框相同。不含关键点的模型不回读这一段。
- 统计：最终目标数、超过阈值的候选数、因容量丢弃的候选数。

容量固定（目标 300 个，每个目标最多 32 个关键点），与性能方案 5.1 的固定容量后处理一致。分割掩码因体积和回读成本另行设计，不在本版本内。

### 4.3 解码器契约

解码器把推理输出张量解码为 4.2 的结果。实时路径上的约束：

1. 只在宿主给定的 CUDA stream 上排队工作，不调用任何同步接口，不切换设备。
2. 显存在启动时一次分配；每帧不申请、不释放显存。
3. 结果写入宿主提供的显存结构，不得超过容量；溢出时如实填写统计字段。
4. 每帧执行时间计入“后处理”阶段，与其他阶段一样按分位数报告。
5. 读取阈值等运行时参数只能通过每帧传入的参数，不得自行读取外部状态。

接口（阶段 1 为仓库内部的 C++ 接口）：

```cpp
class OutputDecoder {
 public:
  virtual ~OutputDecoder() = default;
  virtual const char* Name() const = 0;
  virtual int NumClasses() const = 0;
  virtual int NumKeypoints() const = 0;
  // 实时路径：在 stream 上排队解码，结果写入 output（显存）
  virtual void Enqueue(const float* modelOutput, const DecodeParams& params, DetectionOutput* output,
                       cudaStream_t stream) = 0;
};
```

### 4.4 内置解码器

| 名称 | 输出形状 | 处理 | 正确性基准 |
| --- | --- | --- | --- |
| `yolo-anchors` | `[1, 4 + nc, N]` | 单标签筛选、按类别 NMS（现有实现） | 重构前后 COCO mAP 相同；同一输入与 Python 参考一致；候选不溢出时结果可重复 |
| `yolo-end2end` | `[1, K, 6]`，每行 `x1, y1, x2, y2, score, cls` | 阈值筛选，无 NMS | Python 参考解码在同一引擎输出上一致；COCO mAP 记录 |
| `yolo-pose-anchors` | `[1, 4 + 1 + 3k, N]` | 同 `yolo-anchors`，附带关键点 | Python 参考解码一致；参考解码与 Ultralytics 对同一 ONNX 的预测一致 |

三种实现覆盖“需要 NMS / 不需要 NMS / 附带每目标数据”三种情况，用来检验 4.3 的接口是否站得住。

`yolo-anchors` 原定的“重构前后逐框一致”无法作为基准：重构前的实现在分数并列时按候选写入位置（原子操作的先后）排序，同一程序两次运行就有 2362 张图结果顺序不同。重构中改为以锚点号为第二键（性能方案 5.1），因此改用上表三项。

验收结果（2026-10-26，RTX 4050 Laptop）：

| 解码器 | 模型 | 同一输入与 Python 参考 | 其他 |
| --- | --- | --- | --- |
| `yolo-anchors` | YOLO26n FP16 | 200 张一致率 1.000 | COCO 5000 张 mAP50-95 40.31、mAP50 56.01，与重构前相同；候选不溢出的 4537 张两次运行完全一致 |
| `yolo-end2end` | YOLO26n 端到端 FP32 | 200 张一致率 1.000 | COCO 5000 张 mAP50-95 40.24、mAP50 55.78；输出已按分数降序，参考解码与 Ultralytics 预测逐框相同 |
| `yolo-pose-anchors` | YOLO26n-pose FP32 | 200 张一致率 1.000；关键点坐标最大差 0.00006 px，分数最大差 1e-6 | 参考解码与 Ultralytics 对同一 ONNX 的预测一致（关键点裁到图像内后） |

空载端到端（144 FPS 测试源）：一对多头 FP16 取得→结果 P50 1.48 ms、P95 2.50 ms，与重构前一致；端到端头 FP32 为 2.51 / 3.74 ms，姿态 FP32 为 3.17 / 4.24 ms（两者只有 FP32 版本，推理本身分别约 2.0 与 2.5 ms）。

### 4.5 解码器插件的对外 ABI（阶段 4）

接口稳定后以纯 C ABI 公开，原生插件为 DLL：

- 导出单个查询函数，返回函数表；函数表与所有参数结构的第一个字段为结构大小，后续版本只追加字段。
- 跨边界只传 C 结构、指针与 UTF-8 字符串，不传 C++ 对象、STL 容器或异常。
- 插件声明所需的接口版本，宿主拒绝不兼容的插件并在界面说明原因。
- 原生插件与宿主同进程，享有完全权限；宿主只加载用户显式放入插件目录的 DLL。

## 5. 第 2 层：结果发布

### 5.1 机制

宿主在每帧结果可用后，把结果写入一块命名共享内存，并通知等待者。任何语言的程序都可以读取，读取方崩溃或卡顿不影响检测。

- 共享内存：`Local\NeuralReflex.Results.v1`。
- 通知：两个手动重置事件 `Local\NeuralReflex.Results.v1.Event0`、`...Event1`。第 k 帧发布时，宿主先重置 `Event[(k+1) % 2]`，写入数据，再设置 `Event[k % 2]`。读取方读完第 s 帧后等待 `Event[(s+1) % 2]`。这样任意数量的读取方都不需要注册，也不会空转。
- 一致性：序号锁（seqlock）。写入前序号加一（变为奇数），写完再加一（变为偶数）；读取方复制前后读到的序号相同且为偶数，才算读到完整的一帧。

### 5.2 布局（版本 1）

所有字段小端序，偏移固定：

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0 | `uint32` | 魔数 `0x5352524E`（字节序列 `NRRS`） |
| 4 | `uint32` | 布局版本，1 |
| 8 | `uint32` | 映射总字节数 |
| 12 | `uint32` | 帧记录偏移 |
| 16 | `int64` | 帧序号锁（偶数时帧记录完整，已发布帧数 = 序号 / 2） |
| 24 | `int64` | 元数据序号锁 |
| 32 | `uint32` | 元数据偏移 |
| 36 | `uint32` | 元数据容量 |
| 40 | `uint32` | 元数据实际长度 |
| 44 | `uint32` | 宿主进程号 |
| 48 | `int64` | QPC 频率 |

元数据为 UTF-8 JSON，会话开始时写入（`state` 为 `running`），结束时改写为 `stopped`：

| 字段 | 含义 |
| --- | --- |
| `layout` | 布局版本 |
| `session` | 会话号（开始时刻的 Unix 毫秒数） |
| `state` | `running` 或 `stopped` |
| `pid` | 宿主进程号 |
| `model` | 模型文件名（不含扩展名） |
| `decoder` | 解码器名称 |
| `inputSize`、`numClasses` | 模型输入边长、类别数 |
| `classNames` | 类别号 → 名称 |
| `keypoints` | `count`、`names`、`skeleton` |

帧记录：

| 类型 | 字段 |
| --- | --- |
| `uint64` | 会话内帧号 |
| `int64` | 取得画面时刻（QPC） |
| `int64` | 结果可用时刻（QPC） |
| `int32 × 4` | 检测区域 x, y, w, h（屏幕物理像素） |
| `int32` | 目标数 |
| `int32` | 每个目标的关键点数 |
| `int32` | 超过阈值的候选数 |
| `int32` | 因容量丢弃的候选数 |
| 目标 × 300 | `float32 x1, y1, x2, y2, score; int32 cls`（24 字节），只有前“目标数”个有效 |
| 关键点 × 300 × 32 | `float32 x, y, score`（12 字节），第 i 个目标的第 j 点位于 i × 关键点数 + j |

时间戳用 QPC，读取方可与自己的 `QueryPerformanceCounter` 直接比较，计算结果到达自身的延迟。

### 5.3 代价与约束

- 发布在完成线程上进行，只做一次内存复制和一次事件操作，不分配内存、不加锁、不等待读取方。
- 关闭发布时不创建共享内存。
- 读取示例见 `tools/results/read_results.py`，只依赖 Python 标准库。
- 映射已存在时：发布进程仍在运行则本会话不发布并说明原因，检测照常；发布进程已退出（读取方仍持有映射）则接管，保留序号，读取方以元数据中的会话号区分新旧会话。

验收结果（2026-10-26）：

- 离线模式发布 200 张 COCO 图片，读取方收到的 170 帧（其余发生在读取方打开映射之前）与检测输出逐帧一致，含关键点。
- 实时 144 FPS：读取方收到每一帧，漏帧 0；送达延迟（结果可用 → 读取方取得）P50 约 0.05 ms、P99 约 0.13 ms。
- 读取方运行中被强制结束、随后新读取方接入：检测速率与延迟无变化，新读取方漏帧 0。开启发布时取得→结果 P95 2.57–2.62 ms，未开启时 2.50 ms。
- 另一个进程正在发布时，第二个进程报告占用并照常检测；占用者退出后可再次发布。

### 5.4 后续

本地 WebSocket（便于网页与远程工具接入）在共享内存稳定后加入，作为它的一个读取方实现，不进入完成线程。

### 5.5 外部进程插件（阶段 3）

结果读取方由宿主托管时即为外部进程插件：宿主发现、启动、停止它，崩溃后重启，在界面中显示状态、指标与日志，并把用户设置传给它。插件进程与检测完全隔离，崩溃或卡顿不影响检测，可以用任何语言编写。

**插件包**：一个文件夹，内含 `plugin.json` 与入口程序。宿主在以下目录查找（后者覆盖同 `id` 的前者）：程序目录下的 `plugins`、源码树根目录的 `plugins`（开发时）、`%LOCALAPPDATA%\NeuralReflex\plugins`（用户安装）。

| 字段 | 含义 |
| --- | --- |
| `schema` | 清单格式版本，1 |
| `id` | 唯一标识，小写字母、数字、`-`、`.` |
| `name`、`version`、`description` | 显示用 |
| `api` | 插件协议版本（本节的环境变量、输出协议与 5.2 的结果布局），当前为 1；不等于宿主支持的版本时标为不兼容，不启动 |
| `entry.command` | 可执行文件。含路径分隔符或在插件目录中存在时相对插件目录，否则在 PATH 中查找（如 `python`） |
| `entry.args` | 参数数组，工作目录为插件目录 |
| `settings` | 设置项声明，见第 6 节 |

**生命周期**：启用的插件在宿主启动时启动，与检测会话是否运行无关（插件自行等待结果出现）。有启用的插件时，检测会话自动发布结果。进程异常退出后按 1、2、4…30 s 退避重启；60 s 内退出 5 次则标为失败，不再重启，直到用户重新启用。停止时先关闭插件的标准输入，2 s 后仍未退出则结束进程。插件进程加入宿主的作业对象，宿主退出时一并结束。

**宿主 → 插件**：环境变量。

| 变量 | 内容 |
| --- | --- |
| `NR_PLUGIN_ID` | 插件 `id` |
| `NR_PLUGIN_DIR` | 插件目录 |
| `NR_PLUGIN_DATA` | 插件可写的数据目录（`%LOCALAPPDATA%\NeuralReflex\plugin-data\<id>`） |
| `NR_PLUGIN_SETTINGS` | 设置值，UTF-8 JSON 对象；设置修改后插件重启 |
| `NR_RESULTS_MAPPING` | 结果共享内存名（5.1） |
| `PYTHONPATH` | 前置 Python SDK 目录；同时设置 `PYTHONUNBUFFERED=1`、`PYTHONIOENCODING=utf-8` |

**插件 → 宿主**：标准输出，每行一个 UTF-8 JSON 对象；不是 JSON 的行按日志处理，标准错误按错误日志处理。

| `type` | 字段 | 宿主处理 |
| --- | --- | --- |
| `status` | `text` | 显示为插件当前状态 |
| `metric` | `key`、`value`、可选 `label`、`unit` | 显示在插件详情中，同 `key` 覆盖 |
| `log` | `text`、可选 `level`（`info`、`warning`、`error`） | 保留最近 200 行 |
| `notify` | `text` | 在界面弹出提示，每个插件至多每 2 s 一次 |

**SDK**：`sdk/python/neural_reflex.py`，只依赖标准库，封装设置读取、上述输出协议与结果读取（5.1 的序号锁与事件等待、会话切换）。`tools/results/read_results.py` 使用同一实现。示例插件 `plugins/target-alert`：指定类别的目标连续出现一段时间后提示，并可记录到 CSV，设置项覆盖全部四种类型。

验收结果（2026-10-26，在真实桌面程序中通过 WebView2 远程调试操作界面）：

- 发现与启用：程序发现源码树中的示例插件；在界面中启用后插件以宿主为父进程启动，未开始检测时显示“等待检测开始”。
- 端到端：在桌面程序中开始检测后，因有启用的插件而自动发布结果；插件处理 142.7 帧/秒，送达延迟中位数 0.074 ms；告警按 10 s 间隔触发，界面弹出提示，`alerts.csv` 写入记录。插件运行时检测 144.9 次/秒，取得→结果 P95 1.97 ms。
- 设置：在界面修改“告警类别”后插件收到停止请求、以代码 0 退出并按新设置重启；设置写入宿主设置文件。
- 崩溃策略：连续强制结束 5 次，前 4 次分别在 1、2、4、8 s 后重启，第 5 次标为失败并说明原因；点“重启”后恢复运行。
- 不兼容与无效：协议版本 2 的插件标为不兼容、开关不可用；`settings` 含未知类型的插件标为清单无效并给出原因；两者均不启动。
- 停止：关闭开关后插件以代码 0 退出；关闭桌面程序后插件进程随之结束。

测试中注意到：主窗口最小化时宿主令 WebView2 不可见（`put_IsVisible(false)`），页面暂停处理消息，恢复后由下一条完整快照追上，不需要补发。

## 6. 第 3 层：设置与界面

插件不能修改宿主界面的结构与脚本：宿主界面掌握模型、采集目标与调度设置，插件脚本进入宿主页面即获得全部控制权，也会在宿主界面更新时失效。插件只能通过以下贡献点出现在界面中：

| 贡献点 | 方式 | 阶段 |
| --- | --- | --- |
| 插件管理页 | 宿主列出全部插件：名称、版本、接口兼容性、启用开关、运行状态、指标、日志 | 3 |
| 设置项 | 清单声明，宿主生成表单；值随宿主设置保存，修改后插件重启 | 3 |
| 插件页面 | 插件提供的 HTML，在隔离的 iframe 中加载，只能通过受限的消息接口与宿主通信 | 5 |
| 概览卡片 | 插件推送的指标以宿主样式显示在概览页 | 5 |
| 覆盖层图元 | 插件提交框、点、线、文字，由宿主绘制 | 5 |

设置项（`settings` 数组中每项）：

| 字段 | 含义 |
| --- | --- |
| `key` | 设置名 |
| `type` | `boolean`、`number`、`string`、`enum` |
| `label`、`description` | 显示用 |
| `default` | 缺省值 |
| `min`、`max`、`step` | `number` 的范围 |
| `options` | `enum` 的选项，`[{"value": ..., "label": ...}]` |

宿主按声明校验类型与范围，不合法的值改用缺省值。

## 7. 插件平台

阶段 3 让外部进程插件能运行起来；本节把它补成一个可以长期演进的平台。目标是通用扩展平台的完整性，而不是为某个插件补齐专用能力：每项公共接口至少用两种不同场景验证（本节用告警、记录、转发三个示例插件）。

### 7.1 原则与边界

- **宿主拥有最终决定权**：采集对象、模型、精度、检测调度、GPU 资源、在途帧数、覆盖层呈现、会话启停与全局配置。插件可以查询、声明需求或通过受控接口请求，不能直接修改全局配置。
- **领域插件自己负责**：业务规则与告警条件、跟踪与聚合、外部系统协议、领域状态与算法。平台不内置某个业务的决策；跟踪只是派生结果的一种，不是所有插件的必经环节，目标 ID 也不是结果的必需字段。
- **速率分开**：检测速率是宿主的全局工作负载配置；某个插件的消费速率是该插件自己的选择（SDK 在读取方限速）；覆盖层更新率是显示配置。三者不由插件设置混为一谈。
- **慢消费者不拖慢平台**：实时消费者只取最新结果，跳过旧帧；记录消费者从有界环形缓冲按序读取，被覆盖时明确知道丢了多少帧。宿主从不等待任何读取方。
- **隔离不等于沙箱**：外部进程隔离防的是故障（崩溃、卡顿、内存泄漏），不是恶意。插件以当前用户的普通桌面程序权限运行，可以自行访问文件、网络和同一会话中的命名共享内存。界面与文档不给出插件“被限制”的暗示；只有经过宿主转发的操作（界面按钮、宿主状态查询、将来的覆盖层图元）才真正受宿主控制。
- **协议先于 SDK**：协议只依赖环境变量、标准输入输出、共享内存与事件，任何语言都能实现。Python SDK 与 C++ SDK 都是协议的实现，不是协议本身。

### 7.2 版本与特性协商（协议 1.1）

协议版本为“主版本.次版本”，当前为 1.1。次版本只做增量；新功能以**特性**为单位按需启用，旧插件不需要升级。

| 清单字段 | 含义 |
| --- | --- |
| `api` | 主版本，1。与宿主主版本不同则不兼容 |
| `features` | 插件依赖的特性；宿主不支持其中任一项则不兼容，并说明缺哪一项 |
| `optionalFeatures` | 宿主支持就启用，不支持就不启用，插件自行降级 |

宿主协议 1.1 支持的特性：

| 特性 | 内容 |
| --- | --- |
| `control` | 控制通道：宿主经标准输入发送事件、设置更新、请求与停止消息（7.4）；插件须报告就绪（7.3） |
| `results.ring` | 结果共享内存带环形缓冲，可按序读取并统计丢帧（7.5） |

新增环境变量：

| 变量 | 内容 |
| --- | --- |
| `NR_API` | 宿主协议版本，如 `1.1` |
| `NR_FEATURES` | 对本插件实际启用的特性，逗号分隔（`features` 与 `optionalFeatures` 中宿主支持的部分） |
| `NR_HOST_VERSION` | 宿主程序版本 |

兼容规则：双方都忽略未知的消息类型与字段；插件以 `NR_FEATURES` 判断启用了什么，不以宿主版本推断。Python SDK 由宿主经 `PYTHONPATH` 提供，在主版本内保持向后兼容；插件也可以把 SDK 复制到自己目录中固定版本（插件目录在 `sys.path` 中先于 `PYTHONPATH`）。结果共享内存的布局版本独立于协议版本，见 5.2 与 7.5。

### 7.3 生命周期

区分“进程已启动”和“插件可工作”。启用了 `control` 的插件启动后处于 `starting`，发出 `ready` 后才进入 `running`；超过 `startTimeout` 未就绪按启动失败处理（计入重启策略）。未启用 `control` 的插件进程启动即视为 `running`（与阶段 3 相同）。插件不跟随检测会话启停，会话变化通过事件通知（7.4）。

| 清单字段 | 缺省 | 含义 |
| --- | --- | --- |
| `startTimeout` | 15000 | 等待就绪的毫秒数，1000–120000 |
| `stopTimeout` | 2000 | 请求停止后的宽限毫秒数，500–30000；超时后结束整个进程树 |
| `restart` | `always` | 未经请求的退出：`always` 按退避重启；`on-failure` 退出代码为 0 时视为正常结束，不重启；`never` 不重启 |

插件 → 宿主新增消息（标准输出，所有插件均可使用）：

| `type` | 字段 | 宿主处理 |
| --- | --- | --- |
| `ready` | — | `starting` → `running` |
| `failed` | `text`、可选 `retry`（缺省 `false`） | 插件即将因无法恢复的错误退出（设置错误、缺少依赖）。`retry` 为 `false` 时标为失败、不再重启，直到用户修改设置或手动重启；原因显示在界面 |
| `health` | `state`（`ok`、`degraded`、`error`）、`text` | 插件自评的健康状态，与进程状态分开显示 |

进程退出未给出原因时，宿主以标准错误的最后一行作为失败原因的一部分（例如 Python 的 `ModuleNotFoundError`）。

每个插件进程放入单独的作业对象（宿主退出时一并结束）：停止超时时结束整个进程树，包括启动器（如 `py.exe`）派生的解释器进程；作业对象同时提供整棵进程树的 CPU 时间与内存，用于诊断（7.6）。

### 7.4 控制通道与请求

控制与数据分离：控制走标准输入输出（每行一个 UTF-8 JSON 对象，单行不超过 1 MiB），每帧数据只走共享内存。宿主对每个插件用独立的写入线程和有界队列（256 条），写入阻塞不影响宿主其他部分；队列满说明插件长期不读标准输入，宿主按无响应处理并重启它。

宿主 → 插件（只发给启用了 `control` 的插件）：

| `type` | 字段 | 含义 |
| --- | --- | --- |
| `event` | `name`、`data` | 事件。`session`：检测会话状态变化，`data` 含 `state`（`idle`、`preparing`、`running`、`failed`；停止检测后为 `idle`）、`session`、`publishing`、`model`；插件启动后立即收到一次当前状态 |
| `settings` | `values` | 只改动了 `live` 设置项时，以此热更新；`values` 为全部设置的新值 |
| `request` | `id`、`method`、`params` | 宿主请求，插件须以 `response` 回答 |
| `cancel` | `id` | 宿主不再等待该请求（超时或用户离开） |
| `response` | `id`、`result` 或 `error` | 对插件请求的回答 |
| `stop` | — | 请求停止；随后宿主关闭标准输入。未启用 `control` 的插件只以关闭标准输入表示停止 |

宿主发出的请求：

| `method` | `params` | 超时 | 用途 |
| --- | --- | --- | --- |
| `action` | `{"id": ...}` | 10 s | 用户点击插件声明的操作按钮（清单 `actions`）。`result` 可含 `text`，显示为提示 |
| `diagnose` | `{}` | 3 s | 导出诊断时收集插件自述的状态，`result` 原样写入诊断文件 |

插件 → 宿主的请求（`request`，宿主在读取线程中立即回答，不做阻塞操作）：

| `method` | `result` |
| --- | --- |
| `host.info` | `version`、`api`、`features` |
| `session.state` | 与 `session` 事件的 `data` 相同 |

错误为 `{"code": ..., "message": ...}`，`code` 取 `unknown_method`、`invalid_params`、`timeout`、`busy`、`failed`。每个插件同时至多 16 个未完成的宿主请求，更多时直接以 `busy` 失败。未知 `method` 一律回答 `unknown_method`（SDK 自动处理）。

清单 `actions`：`[{"id", "label", 可选 "description", 可选 "confirm"}]`，`confirm` 为确认文字，界面先请用户确认再发请求。只有启用了 `control` 时显示。

设置项 `live: true` 表示可热更新：只改了这类设置项时宿主发 `settings` 消息，不重启；改动了其他设置项，或插件未启用 `control`，仍按阶段 3 重启。界面标明每个设置项是“立即生效”还是“重启插件”。

### 7.5 数据契约与环形缓冲

结果的坐标、时间与会话语义见 4.2、5.2：坐标为屏幕物理像素，时刻为 QPC，帧号在会话内从 0 递增，会话以元数据中的 `session` 区分。元数据另加 `coordinates: "screen-physical"` 与 `clock: "qpc"`，把这些约定写进数据本身。

环形缓冲是 5.2 布局的兼容扩展（布局版本仍为 1，旧读取方不受影响）：

- 头部偏移 56 的 `uint32` 为环形区偏移（0 表示没有环形区），偏移 60 保留为 0。宿主因此把帧记录偏移移到 128；读取方本来就按头部给出的偏移读取。
- 环形区开头 64 字节：`uint32` 槽数、`uint32` 槽跨度（字节）、`uint32` 槽内帧记录偏移，其余为 0。当前 128 槽，144 帧/秒时约 0.9 s，60 帧/秒时约 2.1 s；读取方以环形区头部为准，不假定槽数。
- 每个槽开头为 `int64` 槽序号，帧记录格式与最新帧记录相同。第 k 次发布（发布后已发布帧数为 k）写入槽 `(k - 1) % 槽数`：先把槽序号置为 `2k - 1`，写入，再置为 `2k`。写入发生在帧序号锁的奇数期间，读取方看到已发布帧数 ≥ k 时第 k 帧已写完。
- 起点：读取方打开映射时，若元数据 `state` 为 `running`，从环形缓冲中属于当前会话（槽内会话号）的最早一帧开始，留出 1/8 槽的余量；否则从下一次发布开始。宿主创建映射与插件打开映射之间发布的帧因此不会漏掉，也不会回放已停止会话的帧。
- 按序读取：读取方要读第 k 帧时读槽序号 s1，等于 `2k` 才复制，复制后槽序号仍等于 s1 才有效；槽序号大于 `2k` 说明已被覆盖，读取方跳到仍在缓冲中的最早帧，并把跳过的帧数计为丢失。

两种接收策略由读取方选择，宿主不区分：`latest` 只取最新帧（实时消费者，跳过的帧计为“跳过”）；`all` 按序读环形缓冲（记录消费者，覆盖导致的缺口计为“丢失”，并随帧告知缺口大小）。宿主每帧多一次有效部分的内存复制，不加锁、不等待。容量之外不提供更强的保证：需要完整记录的场景应让记录插件只做落盘，或降低检测速率。

### 7.6 日志、指标与诊断

- **分清宿主与插件**：插件的消费情况由 SDK 自动上报保留指标（每秒一次）：`nr.fps` 处理帧率、`nr.latency` 送达延迟中位数、`nr.process` 每帧处理耗时 P95、`nr.skipped` 累计跳过帧、`nr.lost` 累计丢失帧。宿主对 `nr.` 前缀的指标使用固定标签，单独显示为“消费”。宿主另按作业对象测量插件进程树的 CPU 占用与内存，显示为“资源”。
- **结构化日志**：`log` 消息可带 `fields` 对象，界面以 `键=值` 附在文字后。每个插件每秒至多 100 行（允许 200 行突发），超出的行丢弃并每秒汇总一条警告，防止逐帧日志拖累宿主与界面。日志同时写入 `%LOCALAPPDATA%\NeuralReflex\logs\plugins\<id>.log`（1 MiB 轮换，保留一个旧文件），插件崩溃后仍可查看。
- **诊断导出**：插件页“导出诊断”写出一个 JSON 文件到 `%LOCALAPPDATA%\NeuralReflex\diagnostics`：宿主版本、系统、GPU、当前会话统计、宿主设置、每个插件的清单、状态、指标、资源、最近日志与 `diagnose` 回答。敏感设置项不导出。

### 7.7 开发与测试工具

- `nr_publish`：用宿主的同一个发布实现写结果共享内存，可生成合成目标或回放 `read_results.py --jsonl` 的记录，可模拟多个会话与会话间隔。没有 GPU 和模型也能开发、测试插件。
- `nr_plugin_run`：以命令行运行宿主的同一个插件托管实现，托管单个插件，把状态、日志、指标与提示逐行输出为 JSON；从标准输入接收操作、设置、重启、停止命令；`--check` 只校验清单。
- 协议测试 `tests/plugins`：用上述两个工具与一组测试插件验证特性协商、就绪与启动超时、`failed`、重启策略、停止超时与进程树、热更新、请求与超时、日志限流、环形缓冲按序读取与丢帧统计。只依赖 Python 标准库。

### 7.8 SDK 与示例插件

| SDK | 内容 |
| --- | --- |
| `sdk/python/neural_reflex.py` | 只依赖标准库。设置、输出协议、控制通道（事件、热更新、操作、请求）、就绪与失败、`frames(mode, max_fps)` 与保留指标 |
| `sdk/cpp/neural_reflex.hpp` | 只有头文件，依赖 nlohmann/json。与 Python SDK 功能对应，用于证明协议与语言无关，也适合低延迟插件 |

| 示例插件 | 语言 | 场景 | 用到的能力 |
| --- | --- | --- | --- |
| `target-alert` | Python | 告警：实时消费 | `latest`、热更新、操作按钮、提示 |
| `result-recorder` | Python | 记录：不漏帧或知道漏了哪些 | `all` 与环形缓冲、丢帧标记、健康状态、优雅停止、操作按钮 |
| `udp-forward` | C++ | 转发到其他系统：低延迟、限速 | `latest` 与读取方限速、热更新、网络 |

验收结果（2026-10-26，RTX 4050 Laptop，YOLO26n FP16，144 FPS 测试源）：

- 协议测试：`tests/plugins` 42 项全部通过（Python 与 C++ SDK 各跑一遍结果读取测试；示例插件测试覆盖记录、告警与转发）。
- 桌面程序中通过 WebView2 远程调试操作界面，三个示例插件同时运行：记录插件按 `all` 收到每帧（丢失 0）；告警插件按 `latest` 处理 143 帧/秒；转发插件按 60 帧/秒限速，接收端每秒 60 个数据报，其余计为跳过。三者送达延迟中位数 0.03–0.08 ms。
- 热更新：修改 `live` 设置项（告警类别、间隔，转发速率）进程号不变并立即生效；修改转发端口（非 `live`）插件重启，接收端随之切换。
- 操作按钮：新建文件、测试提示即时回答；带确认文字的“删除旧记录”第一次点击变为确认文字，第二次才发请求。
- 诊断导出：文件含宿主版本、系统、GPU、会话统计、设置与三个插件的清单、状态、日志和 `diagnose` 回答。
- 崩溃策略：连续强制结束 5 次，前 4 次重启，第 5 次标为失败并给出原因；“重启”后恢复。关闭桌面程序后全部插件进程结束。
- 空载延迟：三个插件运行时取得→结果 P50 1.25 ms、P95 1.81–1.83 ms；不启用插件且不发布时 P50 1.25 ms、P95 1.80 ms，检测速率均约 144 次/秒，不退化。

验收中修正的问题：

- 记录插件在会话开始后才打开映射（SDK 每 0.2 s 重试），此前已发布的约 10 帧仍在环形缓冲中却被跳过且不计为丢失。两个 SDK 改为按 7.5 的起点规则读取，并增加对应测试。
- 桌面程序停止检测时同步更新了界面阶段，定时器因此看不到阶段变化，插件收不到 `idle` 事件，记录插件在会话结束后不关闭文件。开始与停止检测时改为直接通知插件。

### 7.9 使用体验（阶段 7）

**设置体系**，在第 6 节基础上保持声明式、可校验，不开放脚本生成设置页：

| 字段 | 含义 |
| --- | --- |
| `group` | 分组名；同组的设置项显示在一起，按首次出现排序 |
| `visibleWhen` | `{"key": 值或值数组}`，全部满足才显示；隐藏的设置项仍保留值 |
| `aliases` | 旧的 `key` 列表；读取保存的值时按别名迁移，用于设置项改名 |
| `pattern` | `string` 的正则（ECMAScript 语法），不匹配时使用缺省值 |
| `live` | 见 7.4 |
| `type: "secret"` | 敏感字段：以 DPAPI（当前用户）加密后存入宿主设置；界面只显示是否已设置；不出现在诊断与导出中。插件仍经 `NR_PLUGIN_SETTINGS` 收到明文 |

插件详情页提供“恢复默认”“导出设置”“导入设置”（JSON 文件，不含敏感字段；导入时按声明校验）。

**界面贡献点**：操作按钮（7.4）；概览卡片：清单 `overview` 列出至多 4 个指标键，运行中的插件以宿主样式显示在概览页。插件页面（隔离 iframe）与覆盖层图元仍按第 6 节放在阶段 5，单独设计与验收。

**安装、升级与回退**：插件页“安装插件”选择 `.zip` 包或含 `plugin.json` 的文件夹。宿主先解到暂存目录校验：清单有效、`id` 合法、入口存在、不含指向包外的路径、协议兼容；通过后再放入用户插件目录。同 `id` 已安装时先停止它，把旧版本移到 `plugin-backup\<id>`（保留一个版本），界面提供“回退到 x.y.z”。用户安装的插件可以卸载；卸载不删除数据目录。目录用途：

| 目录 | 用途 |
| --- | --- |
| 程序目录 `plugins` | 随程序发布的插件，只读 |
| `%LOCALAPPDATA%\NeuralReflex\plugins` | 用户安装的插件，同 `id` 覆盖程序自带的 |
| `%LOCALAPPDATA%\NeuralReflex\plugin-data\<id>` | 插件数据，升级、回退、卸载都保留 |
| `%LOCALAPPDATA%\NeuralReflex\plugin-backup\<id>` | 上一个版本，用于回退 |
| `%LOCALAPPDATA%\NeuralReflex\logs\plugins` | 插件日志 |

依赖检查：入口程序找不到时给出具体原因（例如“在 PATH 中找不到 python，此插件需要 Python 3”）；插件自身依赖（Python 包等）由插件启动时检查，以 `failed` 消息报告，不由宿主猜测。

**用途声明**：清单 `uses` 从固定词表中列出插件会做的事：`network`（网络连接）、`files`（读写插件数据目录以外的文件）、`processes`（启动其他程序）、`sound`（播放声音）。界面如实显示为“插件声明的用途”，并注明宿主不据此限制插件。

**资源限制**：用户可在插件详情中为每个插件设置内存上限（MB）与 CPU 占用上限（%），由作业对象强制执行；达到内存上限时插件的内存分配失败，通常随之退出并按重启策略处理。

### 7.10 暂不实施的方向

以下各项独立评估，有明确需求与两个以上用例时再单独设计，不与本节捆绑：

- **新结果类型**（旋转框、分割）：随第 1 层解码器增加；共享内存以新的布局版本或新的映射名发布，旧布局继续可用。
- **图像通道**：涉及显存所有权、复制成本与访问控制。若实施，应以不具名的共享句柄只交给声明了该特性的插件，而不是再建一个任何进程都能打开的命名映射。
- **派生结果发布**（插件发布统计、规则事件供其他消费者使用）：先提供明确的数据类型、来源与订阅关系，不演变为任意节点互连的管线图，避免循环依赖与不可控延迟。
- **解码器插件 ABI**：阶段 4，见 4.5。
- **插件页面与覆盖层图元**：阶段 5，见第 6 节。

## 8. 许可证

本项目以 AGPL-3.0 发布。同进程加载的原生插件（4.5 的解码器插件）通常会被认定为与宿主构成整体作品，需要使用兼容的许可证。外部进程插件（5.5）通过共享内存、环境变量与标准输出交换数据，边界较清楚。公开 ABI 前需确认这一点并写入插件开发说明；本节不构成法律意见。
