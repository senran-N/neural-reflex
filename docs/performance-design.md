# Windows 实时视觉检测软件：极限性能设计方案

文档状态：设计方案，尚未实施或完成性能验收。  
调研日期：2026-10-25。  
目标平台：Windows 10/11 桌面环境、支持所选推理后端的 NVIDIA RTX GPU。

## 1. 目标与范围

构建面向屏幕和窗口画面的实时目标检测软件，在高显存占用软件同时运行时持续输出检测框。以至少 144 FPS 的有效检测更新能力为基础目标，继续降低处理延迟、帧间抖动和对并行软件响应速度及任务吞吐的影响。

适用场景包括三维建模与渲染、视频剪辑、科学可视化、本地 AI 推理等。被采集的窗口与产生显存压力的软件可以不同，方案不依赖某一类应用的专用接口。

优化对象是“新画面到可见检测框”的完整链路，包括采集、数据交接、预处理、推理、后处理、绘制和呈现。单独推理的峰值吞吐不作为整机验收结论。

优化必须保持约定的检测精度与检测范围。缩小范围、降低输入分辨率、减少实际推理次数，均须作为不同配置单独记录，不能混入同一性能结果。跟踪预测或插值产生的框不计作新的检测结果。

本文只定义通用的模型接入契约，不绑定具体模型文件、来源、类别或既有测试数据。为使性能目标可验收，另行定义参考基准档位（见 7.2）。

### 1.1 主要风险

| 风险 | 影响 | 应对位置 |
| --- | --- | --- |
| 跨进程 GPU 争用 | 并行软件占满 GPU 时，本程序工作需等待 WDDM 时间片，延迟尾部可达毫秒级 | 6.4 |
| 显存超出预算 | 资源被迁移到系统内存，出现长停顿 | 6.3、6.4 |
| 采集方式降级目标程序呈现模式 | 目标程序由独立翻转退回合成模式，自身延迟上升 | 4.1、5.2 |
| 每帧互操作映射与隐式同步 | 增加固定开销和 CPU 等待 | 4.2 |
| CPU 节流与降频 | 线程被调度到能效核或进入节能状态，抖动增大 | 6.5 |
| 模型规模不受约束 | 144 FPS 目标无法判定 | 7.2 |

## 2. 总体技术路线

采用 C++ 原生核心、GPU 内图像处理、固定资源复用、有限在途任务和独立呈现调度。

```mermaid
flowchart LR
    A[屏幕或窗口 GPU 纹理] --> B[共享资源与 fence 同步]
    B --> C[GPU 融合预处理]
    C --> D[优化推理引擎]
    D --> E[GPU 解码与去重]
    E --> F[共享框缓冲]
    F --> G[Direct3D 批量绘制]
    G --> H[DirectComposition 呈现]
```

CPU 负责生命周期、任务提交、资源所有权和低频统计。图像数据及主要中间结果保留在 GPU；性能计数等少量信息可异步回读。

| 模块 | 设计选择 | 目的 |
| --- | --- | --- |
| 核心程序 | C++、Release 构建、编译优化 | 控制调度、分配及调用开销 |
| 图形 API | Direct3D 11 为主线；Direct3D 12 仅在 CiG 实验分支引入 | 与采集 API 原生衔接，控制复杂度 |
| 采集 | Windows.Graphics.Capture（窗口模式）与 DXGI Desktop Duplication（显示器模式）对比选型 | 获取 GPU 表面，并天然排除覆盖层 |
| 资源交接 | CUDA 外部内存与外部信号量导入共享资源和共享 fence | 避免整帧经过 CPU，避免每帧映射 |
| 预处理 | 融合 CUDA 内核或 D3D11 计算着色器 | 合并裁剪、采样、颜色转换、归一化和布局转换 |
| 推理 | 原生 TensorRT 系列接口 | 针对设备、输入形状和精度优化执行 |
| 提交优化 | CUDA Graph、固定输入输出地址 | 减少重复提交内核的开销 |
| 后处理 | 独立 GPU 解码、筛选及 NMS | 减少回读和 CPU 同步 |
| 覆盖层 | Direct3D、DirectComposition、可等待交换链 | 降低绘制和呈现排队延迟 |
| 设置界面 | 原生桌面控件或 Qt Widgets | 配置及统计与实时处理分离 |

采集、CUDA 和呈现优先使用同一物理 GPU，以设备 LUID 核对适配器。显示输出的实际归属在启动时检查；混合显卡笔记本等跨适配器场景，传输必须计入性能报告，不能当作共享资源的无成本访问。

## 3. 推理技术选型

### 3.1 TensorRT for RTX

优先评估 TensorRT for RTX。官方文档说明其针对 RTX 客户端部署提供硬件专用编译、运行时缓存和 CUDA Graph 支持。近期版本还包含 Windows 下 batch=1 卷积以及算子融合优化。[1][2]

实施要求：

- 针对部署设备构建和预热引擎，验证本机专用构建的收益。
- 实时运行前完成编译、资源分配和内核预热；运行时即时编译的结果写入运行时缓存，避免首次运行或形状变化时在实时路径中编译。
- 固定常用输入形状，以 batch=1 保持逐帧低延迟。
- 复用执行上下文、输入输出缓冲和工作空间。
- 缓存按引擎、设备、运行时版本、驱动兼容性及执行模式管理，失配时重建。
- 确认完整计算路径使用预期后端，禁止未记录的 CPU 回退。

传统 TensorRT 作为性能对照。两者使用相同输入、精度、后处理、采集范围和高显存占用负载比较，最终发布路径保留综合表现更好的实现。新版本或新名称本身不构成性能证据。

### 3.2 精度优化

按 FP32 正确性基准、FP16 优化、INT8/FP8 量化评估的顺序推进。FP16 转换与低比特量化分别处理；后者需要代表性数据校准，并检验检测质量。

TensorRT for RTX 使用强类型网络，执行精度由模型图明确表达。不能假定加载浮点模型后，仅靠运行开关就会自动得到低精度网络。量化使用显式 Q/DQ 节点，工具链可采用 NVIDIA Model Optimizer。[3]

低比特格式受 GPU 架构限制，FP8 等格式须先确认目标设备支持。batch=1 的轻量卷积检测器常受内核调用开销与访存限制，低比特量化的收益可能有限；应先完成 FP16 与 CUDA Graph 路径，再以时间线数据判断量化是否值得投入。

选择精度时同时记录延迟、显存、漏检、误检和框位置变化。保留对精度敏感的运算，只有达到预先约定质量门槛的版本才参与最终速度排名。原始模型保持不变，优化产物独立保存。

### 3.3 CUDA Graph

固定形状、稳定缓冲地址和重复执行模式适合评估 CUDA Graph。其主要作用是减少 CPU 与驱动重复提交 GPU 运算的开销，并不增加 GPU 的计算资源。[4]

实施要求：

- 使用专用的非默认 CUDA stream。
- 启动时完成预热、图捕获和首次重放。
- 运行期间保持输入、输出及工作空间地址稳定。
- 为多缓冲方案明确上下文和图的绑定关系，避免地址交替导致重复捕获。
- 图内不包含逐帧内存申请、主机等待或不受支持的动态控制流。
- 初期由推理引擎管理其内部图；外部预处理、后处理通过事件衔接，避免嵌套捕获。
- 用 GPU 时间线确认图实际执行，不能仅根据配置开关认定启用成功。

只有端到端延迟和抖动确实改善才保留该优化。

### 3.4 CUDA in Graphics（可选实验）

CUDA in Graphics（CiG）使 CUDA 工作与图形队列关联，用于研究本程序计算与图形工作之间的调度。[5] 它列为可选实验，不进入主线阶段，原因如下：

- CiG 上下文绑定 Direct3D 12 命令队列，当前版本仅支持 DirectX 互操作。主线采用的 Direct3D 11 采集与覆盖层路径无法直接使用，需要单独的 Direct3D 12 分支。
- CiG 不能赋予独立程序对其他软件图形或计算队列的控制权，也不提供跨进程的显存隔离。本方案的主要争用来自其他进程（见 6.4），CiG 只改善本进程内部计算与图形的协作。
- 并发内核受共享内存上限约束：Ampere/Ada 为 48 KiB，Blackwell 及更新架构仅在高优先级计算队列下可提高到 84 KiB；Turing 不支持。约束会缩小可选内核范围，推理通常慢于普通上下文。

实验前置条件：

- 确认 CUDA、驱动和 SDK 版本满足官方要求，并查询设备的 CiG 支持属性；创建上下文后通过限制查询确认 CiG 实际生效。
- 针对 CiG 单独构建、缓存和预热引擎。
- 验证分配器、图捕获及资源共享之间的兼容性。
- 以持续检测能力、延迟尾部、显存开销和并行软件性能共同决策。

默认以常规 CUDA 路径建立完整基线，只有 CiG 在同负载对比中胜出且收益覆盖 Direct3D 12 分支的维护成本，才成为发布配置。

## 4. 采集与预处理

### 4.1 采集方式选型

两种采集 API 均返回 Direct3D 11 纹理，在同一负载下对比后选型：

| 维度 | Windows.Graphics.Capture（WGC） | DXGI Desktop Duplication（DD） |
| --- | --- | --- |
| 采集对象 | 单个窗口或显示器 | 整个显示输出 |
| 覆盖层排除 | 窗口模式只采集目标窗口，覆盖层天然不在其中 | 合成结果包含覆盖层，需另行排除并验证 |
| 遮挡与移动 | 目标窗口被遮挡或移动时仍可采集其内容 | 只能得到屏幕上可见的合成结果，需自行维护坐标映射 |
| 帧时间戳 | 每帧提供系统相对时间 | 帧信息提供最后呈现时间（QPC） |
| 更新节流 | 新版系统提供最小更新间隔属性，需设为不限制本程序目标速率 | 按桌面更新提供帧 |
| 注意事项 | 黄色边框、光标采集等行为需按系统版本确认可配置性 | 模式切换、安全桌面时访问丢失，需要重建 |

窗口检测模式优先采用 WGC；显示器检测模式两者均评估。[6][7]

两种方式都依赖 DWM 合成画面。采集或透明置顶覆盖层可能使目标程序或并行软件从独立翻转（independent flip）退回合成模式，增加其呈现延迟。首轮验证必须用呈现分析工具记录目标程序与并行软件在采集开启前后的呈现模式和帧间隔，并把这一影响计入“并行软件性能”。

### 4.2 GPU 图像路径与互操作

采集帧需尽快交接到程序控制的 GPU 资源后释放。采集 API 提供的纹理未必能够直接作为长期共享资源使用；允许必要的一次 GPU 内复制，并记录复制区域和同步成本。设计目标是消除整帧的 CPU 往返传输，不宣称整条链路绝对零复制。

互操作采用 CUDA 外部资源接口：[8]

- 启动时创建以 NT 句柄共享的 Direct3D 11 资源，用外部内存接口导入 CUDA 一次，长期复用。
- 同步使用共享的 Direct3D 11 fence，导入为 CUDA 外部信号量。Direct3D 侧写入完成后 signal，CUDA 在自己的 stream 上 wait；反向交接同理。
- 实时路径不使用每帧的传统图形资源映射与解除映射，避免其固定开销和隐式同步。传统接口仅作为兼容性回退并单独记录性能。
- 禁止每帧创建纹理、导入句柄或注册资源。

预处理的写入目标有两种候选，按实测选择：

1. CUDA 内核读取导入的纹理（CUDA array），输出到推理输入的线性缓冲。
2. Direct3D 11 计算着色器完成预处理，直接写入以共享方式导入 CUDA 的线性缓冲，作为推理输入。该方案省去 CUDA 侧纹理对象，但预处理时间计入 Direct3D 队列。

### 4.3 融合预处理

将以下处理尽可能合并在一次 GPU 遍历中：

- 按配置读取检测区域。
- 等比例采样和必要填充。
- 颜色通道转换。
- 数值归一化。
- 输出张量布局与数据类型转换。

保留精确的缩放、填充和屏幕坐标变换参数，用于结果还原。检测区域是用户配置的一部分，性能优化不得暗中改变其范围。

### 4.4 采集边界

覆盖层和设置窗口应排除在采集内容之外，并验证排除是否生效。WGC 窗口模式通过只采集目标窗口满足该要求；显示器模式需单独验证。覆盖层更新不能被误计为新的目标窗口画面。

窗口检测模式通过窗口客户区与采集画面的映射确定区域，处理移动、缩放、DPI 和显示器切换。首轮性能验证覆盖普通桌面窗口、最大化窗口与多显示器布局；其他显示模式的覆盖层可见性经验证后再列入支持范围。

## 5. GPU 后处理与画框

### 5.1 后处理

模型适配层提供输出布局、坐标语义、类别语义和预处理约定。执行器只在已验证的契约下运行，不根据文件名称猜测输出格式。

GPU 后处理依次完成解码、置信度过滤、候选压缩、NMS 和坐标还原。使用固定容量缓冲，设定候选与最终框数量上限，并记录溢出情况。

容量上限可能影响拥挤画面的检测质量，必须纳入精度验证。空结果同样是有效的新结果，应清除旧框。

NMS 作为独立 GPU 阶段实现，不依赖推理后端必然支持内置 NMS。当前调研版本的 TensorRT for RTX 将 NonMaxSuppression 列为未支持层。[2]

### 5.2 低开销覆盖层

使用 Direct3D 批量绘制边框，DirectComposition 负责窗口合成。检测结果写入可共享的 GPU 缓冲，通过共享 fence 交给绘制阶段；评估实例化和间接绘制，减少 CPU 参与。[9]

性能优先的默认表现为边框与必要类别信息。关闭全分辨率预览和无关动画；文字使用预生成字形资源，避免逐帧创建字体或位图。

采用支持的可等待交换链，初始最大帧延迟设为 1，并在呈现机会到来时选择最新就绪结果。通过实测决定是否需要调整队列深度。[10]

覆盖层提交不能反向阻塞推理线程。没有新结果时不把重复绘制计为新检测；结果过期后清除，过期阈值由实际延迟目标配置。

覆盖层对其下方程序呈现模式的影响见 4.1，须与采集影响分开测量。

## 6. 调度与资源所有权

### 6.1 有限在途工作

维护“正在处理”和“最新待处理”两个逻辑位置。新画面可替换尚未处理的旧画面，不覆盖正在被 GPU 读取的资源。

物理缓冲数量与逻辑队列长度分开管理。缓冲池支持采集、计算、绘制交接，但不允许靠扩大队列累积旧帧。

每个资源具备明确状态：空闲、写入中、就绪、计算中、呈现读取中。通过 fence/event 判断是否可复用。只有正确性确认后，才评估无锁结构是否值得引入。

### 6.2 线程职责

| 执行角色 | 职责 | 避免的工作 |
| --- | --- | --- |
| 采集 | 获取新画面、交接纹理、更新最新帧 | 等待推理完成、图像 CPU 转换 |
| 推理提交 | 提交预处理、推理及后处理 | 等待窗口消息、逐帧磁盘写入 |
| 呈现 | 在呈现时机读取最新结果并画框 | 等待尚未就绪的推理结果 |
| 控制界面 | 参数、状态、启停、模型生命周期 | 逐帧像素处理 |
| 统计 | 汇总计数及分位数、异步报告 | 在实时线程同步输出日志 |

不以增加线程数、多路并发推理或提高队列优先级作为默认提速手段。线程、stream 和并发度通过同负载实验选择。

CUDA stream 优先级只作用于本进程内的调度，不是对其他进程或正在执行任务的抢占保证。[11]

CPU 等待 GPU 完成的方式作为显式实验项：阻塞同步降低 CPU 占用，自旋等待可能缩短唤醒延迟。两种方式在同负载下比较延迟尾部与 CPU 开销后选择，不默认自旋。

### 6.3 内存和启动流程

启动阶段完成模型检查、引擎准备、显存申请、纹理共享、字形准备和预热。准备结束后进入实时运行。

实时路径复用缓冲及描述对象，避免重复创建会话、动态装载模块、即时编译、逐帧分配显存、设备级同步和同步文件操作。

模型权重在运行期间保持驻留。根据设备可用显存预算及并行软件占用，为引擎工作空间、输入输出、采集纹理、后处理和覆盖层缓冲设置总预算，同时报告稳态与峰值占用，避免将显存迁移造成的停顿隐藏在平均值中。

显存驻留量、计算占用和显存带宽压力分别记录。高显存占用不能直接等同于计算单元满载；优化需要同时减少本程序的显存需求、传输量和计算时间。在预算内优先复用缓冲，避免通过扩大工作空间或增加在途帧换取短时吞吐。

### 6.4 跨进程 GPU 争用

并行软件占满 GPU 时，各进程的工作由 Windows 图形内核调度器按时间片轮转。这是本方案延迟尾部的首要来源，CUDA stream 优先级与 CiG 都无法跨进程生效。以下手段作为一等实验项，与模型优化同等对待：

- **显存预算监控**：通过 DXGI 适配器查询本进程的本地显存预算与当前使用量，并注册预算变化通知。[12] 使用量接近预算时，先释放可重建的非关键缓冲，再报告降级，避免被动迁移到系统内存。
- **硬件加速 GPU 调度**：分别在开启和关闭系统硬件加速 GPU 调度时测试，记录本程序延迟尾部与并行软件性能。该设置属于系统配置，不由程序修改，只在报告中注明。
- **进程 GPU 调度优先级**：评估提高本进程 GPU 调度优先级类别对延迟尾部的改善，以及对并行软件的代价。[13] 实时级别需要管理员权限，且可能明显损害其他软件与系统响应，不作为默认配置。
- **工作量本身**：缩短单次 GPU 提交的执行时间，可减少每个时间片内等待与被打断的影响。时间线上需区分本程序内核实际执行时间与等待调度时间。

任何提高本程序优先级的配置，都必须同时报告对并行软件的影响；以牺牲并行软件为代价的提速不能单独作为优化收益。

### 6.5 CPU 与电源状态

- 退出 Windows 对本进程的电源节流（EcoQoS），避免程序不在前台时实时线程被降频或调度到能效核。[14]
- 采集、推理提交和呈现线程可注册为多媒体类调度任务，并评估在混合架构 CPU 上限定其运行于性能核。
- GPU 电源管理模式和系统电源计划固定并写入测试条件；帧间空闲导致的 GPU 降频会放大抖动，需在时间线中核对时钟。
- 以上设置均需对比开启前后的结果，未证实收益的不保留。

### 6.6 异常与恢复

实时路径需处理以下事件，并在恢复期间清除过期框、不计入检测 FPS：

- DD 访问丢失（分辨率或模式切换、进入安全桌面）：释放并重建复制接口。
- WGC 采集目标关闭或窗口销毁：停止该会话并通知控制界面。
- 设备移除或 GPU 超时恢复：重建设备、互操作资源、引擎上下文和覆盖层。
- 显示器热插拔、DPI 变化、适配器变化：重新核对 LUID 与坐标映射。

恢复次数、耗时和期间丢失的帧数单独计入报告。

## 7. 性能指标与验收

### 7.1 测量定义

统一使用可关联的帧标识、主机单调时钟（QPC）和 GPU 时间戳。

| 指标 | 定义 |
| --- | --- |
| 新画面 FPS | 采集源新发布画面的速率；重复取同一帧不计入 |
| 有效检测 FPS | 完成实际推理、对应不同来源帧的结果数量除以时间 |
| 绘制提交 FPS | 覆盖层成功提交的绘制次数，单独报告 |
| 结果呈现更新率 | 已呈现覆盖层中采用不同检测结果的更新速率 |
| 采集延迟 | 来源帧时间戳到本程序取得该帧的时间 |
| 软件处理延迟 | 本程序取得帧到该结果提交绘制之间的时间 |
| 结果新鲜度 | 呈现或绘制提交时，结果距其来源时间戳的时间 |
| 并行软件性能 | 交互响应、画面更新间隔、呈现模式、任务完成时间或处理吞吐，按任务选取并比较检测开启前后变化 |
| 资源开销 | CPU、GPU 时间、可用显存预算、显存稳态及峰值、复制量和排队深度 |

来源时间戳优先使用采集 API 提供的值：WGC 帧的系统相对时间、DD 帧信息中的最后呈现时间。[15] 它们仍不等于来源软件实际渲染完成的时间，报告需清楚标注测量起点。

Present 调用完成也不等于像素已经出现在屏幕上。呈现事件可用于分析调度，实际可见延迟需要显示侧验证；没有测量能力时标记未验证。

### 7.2 参考基准档位与目标

为使目标可验收，性能目标绑定以下参考档位，其他模型和配置单独报告：

- 单阶段卷积检测器，计算量与常见轻量级检测模型相当，具体模型与计算量在正确性基线阶段确定并写入报告。
- 输入 640×640，batch=1，FP16。
- 检测区域、类别数和后处理容量上限固定。

目标：

- 在来源画面持续达到相应更新率的动态场景中，有效检测持续达到至少 144 FPS。
- 144 FPS 对应约 6.94 ms 的结果产出节拍；节拍与单帧端到端延迟分别测量。
- 将软件处理延迟 P95 不超过 6.94 ms 作为初始工程目标，同时记录 P50、P99 和最大值。流水线重叠后，延迟可以大于节拍而吞吐仍达标；两项分别判定。
- 可见更新率目标为至少 144 Hz，要求显示链路和画面源具备对应能力。
- 不出现随着运行时间增加而持续增长的队列和结果延迟。
- 满足预先约定的检测质量门槛，记录对高显存占用软件响应速度和任务吞吐的影响。
- 在约定的可用显存预算内运行，记录显存驻留、预算变化和资源迁移期间的延迟。

上述为设计目标，不是已经实现的性能承诺。

### 7.3 延迟预算

以下为空载时的初始分配，用于定位超支阶段，首个端到端原型完成后按实测校准：

| 阶段 | 初始预算（ms） | 说明 |
| --- | --- | --- |
| 采集交接与 GPU 内复制 | 0.5 | 含 fence 等待 |
| 融合预处理 | 0.3 | 单次遍历 |
| 推理 | 3.5 | 参考档位 FP16 |
| 后处理与 NMS | 0.5 | 固定容量 |
| 绘制提交 | 0.5 | 不含显示扫描 |
| 调度余量 | 1.6 | 吸收提交间隙与负载波动 |
| 合计 | 6.9 | 对应 144 FPS 节拍 |

高负载下的超支主要来自跨进程等待（6.4），须在时间线上与各阶段执行时间分开统计。流水线可重叠执行，因此不能简单把各阶段独立基准相加来代替端到端测量。

### 7.4 合成测试源

建立可控的测试程序作为采集源：每帧把帧编号和生成时间戳编码到固定像素区域，并按设定速率呈现已知位置的目标图形。用途：

- 对齐采集帧、检测结果与覆盖层呈现，计算真实的帧对应关系和丢帧。
- 以已知目标位置验证坐标还原与检测正确性。
- 提供可重复的新画面速率，排除来源软件帧率波动。

有条件时使用光电传感器或高速相机，对测试源画面与覆盖层框出现的时间差做抽样测量，作为可见延迟的显示侧验证。

### 7.5 持续负载测试

固定并行软件及其任务、数据规模、显存驻留量、计算负载、处理参数和软件版本；同时固定采集源内容、画面更新率、分辨率、显示刷新率、检测范围、模型精度、硬件加速 GPU 调度设置、GPU 与 CPU 电源状态。

测试覆盖显存长期高占用以及任务执行期间的分配与释放波动，并记录计算和带宽压力。采集源与并行负载分别配置，确保检测结果的变化可以归因于被测优化。

先使设备进入稳定负载，再连续测试至少 30 分钟。记录每秒有效检测速率、每个 60 秒窗口的吞吐，以及全程延迟分位数、长停顿、温度、时钟和显存变化。

对比测试保持同一环境，交替运行配置并重复有效样本，避免把热状态和后台负载变化误判为优化收益。单独记录关闭检测时并行软件的响应、任务耗时、吞吐、呈现模式和显存基线。

FPS 按已完成结果计算；状态栏刷新次数、循环次数、GPU 提交次数和重复画框次数均不能替代。

### 7.6 工具

使用 NVIDIA Nsight Systems 检查 CUDA Graph、内核间空隙、复制、同步、线程等待和上下文切换。使用 PresentMon 记录目标窗口、并行软件与覆盖层的呈现节奏和呈现模式，[16] 并结合并行软件自身的任务计时和资源统计评估影响。

定位瓶颈的采样与最终跑分分开进行，记录分析工具自身的开销。官方推理基准可能默认省略数据传输或采用自旋等待，其结果必须注明测量边界。[17]

## 8. 实施顺序与交付物

| 阶段 | 交付物 | 完成标准 |
| --- | --- | --- |
| 正确性基线 | 模型适配契约、参考档位、代表性验证集、合成测试源、坐标验证结果 | 输入输出含义明确，结果正确 |
| 最小端到端原型 | 采集、预处理、推理、后处理、透明画框的最简实现；首份 Nsight Systems 时间线与 PresentMon 记录 | 同一帧可追踪，没有整帧 CPU 往返；按实测校准 7.3 延迟预算 |
| 采集与互操作选型 | WGC 与 DD 对比、外部内存与 fence 互操作、预处理两种实现对比 | 每项选择有同负载数据支撑 |
| 引擎优化 | 后端对比、FP16 与 CUDA Graph、低精度产物 | 每项优化有可重复的收益证据 |
| 并行负载优化 | 显存预算监控、调度优先级与硬件加速 GPU 调度对比、CPU 电源设置、异常恢复 | 高显存占用软件并行运行时选择最优组合，并报告对并行软件的代价 |
| 可选实验 | CiG 与 Direct3D 12 分支 | 仅在胜出且收益覆盖维护成本时合入 |
| 持续验收 | 长时间测试报告、检测延迟分布、显存曲线及并行软件性能变化 | 按完整目标判定，通过项和未达项明确 |

优化方向以最小端到端原型的时间线为依据决定，不预先按本文列举顺序全部实施。每次优化保留前后结果。最终配置由真实负载下的检测更新率、延迟尾部、显存需求、对并行软件的影响和精度共同决定。

判断是否接近设备能力边界时，必须同时具备：完整数据路径测量、主要后端与精度对比、队列无积压、资源驻留正常，以及持续负载下的 GPU 执行证据。一次未达标不足以认定设备已经到达上限。
